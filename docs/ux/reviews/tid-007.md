# UX review: TID-007 first-run setup

Branch `tid-007-first-run-setup` (reviewed on `tid-007-ux-review`), against `docs/ux/screens/setup.md` and `auth-common.md`. Built with `npm run build`, served by `wrangler dev` on 8798 with a throwaway `--persist-to` directory and a 36-character `SETUP_TOKEN`. Passkey step through Chromium's virtual authenticator. Capture script: `docs/ux/reviews/capture-tid-007.mjs`. Raw measurements: `docs/ux/reviews/tid-007/measurements.json`.

Screenshots are in `docs/ux/reviews/tid-007/` as `{m|d}-{light|dark}-NN-name.png` (`m` is 375x812, `d` is 1280x800).

**Verdict: accept with one major fix.** No blockers. The main risk, losing the codes, is well guarded.

## Findings

### Major

**M1. At large text sizes the sticky footer covers most of the screen on the codes step.** Seen at 200% text on 375x812 (`m-light-13-text200-codes.png`, `m-dark-13-text200-codes.png`). The footer (checkbox, helper, Continue, helper) is about 560 px of 812, so the heading, warning and codes are almost entirely hidden behind it. The user can still scroll, but only a sliver of content is ever visible. This fails the intent of WCAG 1.4.4 / 1.4.10 and makes the step hard to use for exactly the people who set large text.
Fix, in `apps/web/src/auth/RecoveryCodesStep.tsx` line 258: replace `sticky bottom-0 ... md:static` with `static [@media(min-height:40rem)]:sticky bottom-0 ...` (keep `md:static`; order so that `md:static` wins). rem media queries follow the browser's text size, so large text makes the footer static automatically. 375x667 at normal size is 41.7 rem and keeps the sticky footer (it takes about 28% of the screen, fine). Also add `scroll-padding-bottom: 12rem` on the scroll container while the footer is sticky. I checked that tabbing to Download keeps it clear of the footer today (bottom 526, footer top 570), so this is protection, not a current defect. Spec updated (setup.md section 5).

### Minor

**m1. Footer helper text touches the bottom edge.** `m-light-14-short-bottom.png`, `m-light-09-codes-before.png`: "Tick the box to continue." sits flush with the screen edge when the safe-area inset is 0 (it is 0 in every headless run and on most Android phones). The class is `pb-[max(0px,env(safe-area-inset-bottom))]`. Fix: `pb-[max(0.75rem,env(safe-area-inset-bottom))]`. Spec updated to match.

**m2. Rate-limit helper has no full stop and differs from the banner.** Banner reads "Too many attempts. Try again in 10 minutes." but the helper under the button reads "Try again in 10 minutes" (`m-light-04-rate-limited.png`). The spec shows a full stop. Fix: add the period in the helper (shared helper in `ui.tsx` or `Setup.tsx` near line 315).

**m3. Copy and Download are below the first screen, the checkbox is not.** At 375x812 (`m-light-09-codes-before.png`) the first fold shows the warning, the intro and seven codes, with the checkbox and Continue in the sticky footer. Copy and Download need a scroll (at 375x667 they need about 250 px). A user can tick the box and leave without ever seeing the buttons that help them keep the codes. This is how the spec is drawn, so it is not a build defect, but I would move the two buttons above the list for the next pass (they then sit in the first fold on 812 and half in it on 667). It changes the spec in one place, so I have left it for the PM to decide rather than changing it myself.

**m4. `/login` after the redirect shows the placeholder only, not the "already set up" notice.** With an owner in the database, `/setup` redirects to `/login` and shows "Sign in / This screen isn't built yet." (`m-light-16-setup-redirect-login.png`). The notice "This Tidings is already set up. Sign in instead." only appears on the mid-flow 409 path. The spec (section 2.8) requires it for 409 only, and a plain redirect is silent by design, so this is consistent. Noted for TID-008 so the login screen renders the notice from route state.

**m5. Signed-out `/all` does not redirect.** Known and accepted (TID-008 owns it). Recorded only so the tester does not file it.

## Rulings on engineer deviations

1. **Accessible names: agreed.** The three names ("Copy codes, all 10 recovery codes", "Copied 10 recovery codes", "Download .txt file of recovery codes") each begin with the visible label, which satisfies WCAG 2.5.3 Label in Name. My first draft ("Copy all 10 recovery codes") did not contain the visible text "Copy codes", so that was my error. `setup.md` sections 5.2 and 10 now match the build.
2. **No signed-out redirect, placeholder `/login` and `/recover`: accepted** for this story. Both placeholders render "This screen isn't built yet." under the right heading, and the in-app "Already set up? Sign in" link reaches `/login`. See m4 and m5.

## Spec changes made

`docs/ux/screens/setup.md`: accessible names (5.2, 10); footer padding and the sticky-only-when-tall rule with `scroll-padding-bottom` (section 5).
