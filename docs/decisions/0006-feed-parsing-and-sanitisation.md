# 0006. Feed parsing on the Worker, HTML sanitisation in the browser

- Status: **Accepted** (2026-11-16, after spike TID-002; see "PM decision" at the end). Supersedes the provisional parser choice.
- Date: 2026-11-16
- Deciders: product-manager

## Context

Parsing is the most CPU-intensive thing the Worker does and the Free plan allows 10 ms CPU per invocation. Feed HTML is untrusted and must be sanitised before it reaches the DOM. OPML import is a one-off parse of a ~50 KB file.

## Options

- Parser: **htmlparser2 12** (streaming SAX-style callbacks in `xmlMode`; tolerant; can stop early), **feedsmith 3** (complete RSS/Atom/RDF/namespace mapping on top of fast-xml-parser; builds a full object tree), fast-xml-parser 5 directly, native `HTMLRewriter` (fast, but HTML semantics break RSS: `<link>` is a void element in HTML).
- Sanitiser location: Worker at ingestion vs browser at render.
- OPML parse location: Worker vs browser.

## Decision

- **Parse feeds on the Worker with htmlparser2 12** (`xmlMode`) with our own minimal RSS 2.0 / Atom 1.0 / RSS 1.0 mapper in `packages/feed-parser`, with a true early stop after `MAX_ITEMS_PER_FETCH` = 50 items and ignoring elements we don't store. Body cap `MAX_BODY_BYTES` = 1 MiB. Confirmed by TID-002; caps and CPU target in "PM decision" below.
- **Use `HTMLRewriter`** only for feed autodiscovery in website HTML.
- **Sanitise in the browser** with DOMPurify, plus a strict CSP. The server stores raw content (capped at 100 KB) and never renders it.
- **Parse OPML in the browser** (`DOMParser`), send JSON in chunks of ≤ 100 feeds.

## Consequences

- Worker CPU is spent only on extraction; sanitisation cost moves to the client, which has plenty.
- Any future non-browser consumer of `contentHtml` must sanitise it too; the API types document it as raw.
- `packages/feed-parser` is pure TypeScript with no Workers APIs so it can be unit-tested and benchmarked in Node and swapped.

## Results (TID-002, run 2026-11-16)

### Method as run

- Three throwaway Workers on the Workers **Free** plan (`tidings-spike-parse-base`, `-h`, `-f`; all deleted afterwards), same fixtures embedded in each bundle, one bundle per library so cold-start cost isn't mixed. Code in `spikes/tid-002/` on branch `tid-002-parse-spike` (never merged). Fixtures were synthetic (generated by `spikes/tid-002/gen-fixtures.mjs`, lorem ipsum text, deterministic seed) and were **not merged** (PM decision below): `e2e/fixtures/generate-feeds.ts` produces the same sizes on demand.
- Each cell is 200 sequential HTTPS requests for one fixture and one library, in its own UTC minute, from a laptop in Sydney (colo SYD). About 4,800 requests in total.
- **CPU source: Cloudflare GraphQL Analytics API, `workersInvocationsAdaptive.quantiles.cpuTimeP50/P95/P99/P999`** (microsecond resolution, one bucket per minute, so each cell maps to one bucket). Exceeded-CPU counts come from the same dataset (`status = exceededResources`) and were cross-checked against `wrangler tail` events (`outcome: exceededCpu`, integer-ms `cpuTime`). `performance.now()` was not used.
- Library (a): htmlparser2 12.0.0, `xmlMode`, one-shot `write()`, minimal RSS/Atom/RDF mapper (title, link, id, date, summary, content), optional early stop via `parser.pause()` after N items. Library (b): feedsmith 3.0.1 `parseFeed()` (full tree), items sliced afterwards. The cap=50 rows show the effect of stopping early; for feedsmith the cap cannot save CPU because it parses the whole document first.
- Fixture sizes (bytes): small RSS 24,960 (20 items); typical RSS 168,324 (50 items, `content:encoded`); Atom 102,392 (25); RDF 35,512 (30); large RSS 1,116,005 (200); huge RSS 3,327,996 (500).

### Exceeded-CPU outcomes

- htmlparser2, huge, uncapped: **66 of 200 requests exceeded CPU** (69 client-visible HTTP 503s; analytics sampling accounts for the difference). Every other cell, both libraries: **0 exceeded**. Account-wide for the three Workers: 4,765 `success`, 66 `exceededResources`.
- Worth the PM's attention: **many invocations that reported CPU above 10 ms still finished with `ok`.** htmlparser2 typical p99 is 10-13 ms, feedsmith atom p99 is 23-47 ms, and `wrangler tail` showed `outcome: ok` events with `cpuTime` of 20, 23, 32, 67 and 76 ms. Only the uncapped huge fixture on htmlparser2 (p50 29 ms) was killed, and feedsmith on the same fixture (p50 18 ms, p99 66 ms) was not. So the Free plan did not enforce a hard 10 ms cut-off per request in this test. I would not design to that tolerance (the documented limit is still 10 ms and enforcement may change), but it explains why p99 above 10 ms produced no failures.

### Cold start

Single-sample probes, each after a fresh `wrangler deploy` (new isolate), CPU from the GraphQL bucket:

| Bundle | Request on a fresh isolate | CPU ms (samples) |
|---|---|---|
| baseline (no libraries, 5 MB of embedded fixtures) | no-op | 0.33, 0.73 |
| htmlparser2 | no-op (module init only) | 1.13, 0.43, 0.70 |
| feedsmith | no-op (module init only) | 0.53, 0.39, 0.80 |
| htmlparser2 | first parse of `typical` | 22.6, 13.3, 22.1 |
| feedsmith | first parse of `typical` | 38.3, 70.6, 31.1 |

Module initialisation is cheap for both bundles (under 1.2 ms). The cost is the first parse on a cold isolate (JIT and allocation warm-up): about 13-23 ms for htmlparser2 and 31-71 ms for feedsmith. Cron-triggered and fanned-out refreshes will often land on cold isolates, so these figures matter more than the warm p50.

### Findings

1. **htmlparser2 is cheaper than feedsmith everywhere except on bulk text.** Typical: p50 1.3-1.9 vs 2.9-3.1 ms, p95 4.4-5.7 vs 9.5-10.8 ms, p99 10.3-13.0 vs 18.5-27.9 ms. Cold first parse is 2-3x cheaper. feedsmith was faster on the uncapped huge feed (p50 18 vs 29 ms), where htmlparser2's per-chunk string appends dominate. That case is moot if we stop at 50 items.
2. **With early stop at 50 items, htmlparser2's cost is nearly independent of body size:** large capped p50 2.9 / p95 6.4 / p99 10.1 ms; huge capped p50 2.5-3.3 / p95 5.0-6.9 / p99 11.7-12.1 ms; similar to typical. Uncapped, the 1.1 MB fixture is already p50 8.2 / p95 10.2 ms.
3. **The "typical p99 <= 8 ms" target (AC2) was not met by either library.** htmlparser2 p99 was 10.3 (run 1) and 13.0 (run 2); feedsmith 18.5 and 27.9. The p95 <= 5 ms target was met by htmlparser2 in run 1 (4.37) and narrowly missed in run 2 (5.70). The p99 tail is mostly not size-driven: the 25 KB small feed had p99 12.7 ms while the no-op baseline had p99 0.68 ms, so the tail looks like GC and JIT pauses and cold isolates, which caps cannot remove. With 200 samples, p99 is roughly the second-largest value, so it is noisy.
4. Atom and RDF behave like RSS (htmlparser2 Atom p50 1.7-2.0, p99 12.3-12.5; RDF p50 0.9, p99 7.8).

### Limits of this measurement

- Synthetic lorem-ipsum content; real feeds with many entities, namespaces or deeply nested HTML may cost more per byte.
- Parse only. Not included: `fetch()`, reading the body into memory (a 2 MB `text()`), `DigestStream` hashing, dedup, D1 calls. Measure these in TID-011/012 before `MAX_BODY_BYTES` is raised above 1 MiB.
- The mapper is minimal and was not checked for correctness (benchmark only). A production mapper will do slightly more work (date parsing, URL canonicalisation).
- I did not verify that feedsmith returned all 500 items on the huge fixture, so treat its huge numbers as indicative.
- One location (Sydney), one afternoon, one account; Free-plan CPU enforcement may differ at other times.

### Recommendation (for the PM to decide; not applied)

- **Library: htmlparser2**, streaming with early stop. Clear CPU lead on typical feeds and cold starts, and the only one of the two that gets cheaper with a cap.
- **`MAX_ITEMS_PER_FETCH` = 50** (unchanged), implemented as an early stop (`parser.pause()` or abort), not parse-then-slice.
- **`MAX_BODY_BYTES` = 1 MiB (1,048,576)**, down from the spec's 2 MB, until TID-011/012 measure body read plus hash cost. Early stop makes parse cost independent of body size, but the uncapped 1.1 MB fixture was already at the 10 ms edge, and feeds above 1 MiB are rare for a personal reader. Raising it to 2 MiB is reasonable if the body-read cost proves small.
- **Keep the per-item content cap** (the spec's 100 KB), since a few oversized items drive string-append cost.
- **Revisit the CPU target.** A p99 of 8 ms was not reached by any option tested; htmlparser2 measured p95 about 4.4-5.7 ms and p99 about 10-13 ms, with zero exceeded-CPU outcomes except the huge uncapped case. Options: (a) restate the target as p95 <= 6 ms and an exceeded-CPU rate of 0, relying on the observed tolerance, or (b) keep the strict target and cut work further (for example 25 items, or not storing `content:encoded` and fetching article text lazily). I did not measure (b).
- **Huge fixture (AC3):** with `MAX_BODY_BYTES` of 1 MiB or 2 MiB, the 3.3 MB feed is rejected as `too_large` while the body streams in, before any parse. For reference, parsing it uncapped on htmlparser2 is not viable (33% exceeded CPU, p50 29 ms); parsing it with early stop at 50 items costs p50 2.5-3.3 ms and p99 about 12 ms, so it would succeed within caps if the body limit were lifted.

### Cleanup

All three spike Workers were deleted with `wrangler delete` and are absent from the account's script list. No custom domains, routes, D1, KV or other resources were touched.

## PM decision (2026-11-16)

Cloudflare's limits page (checked 2026-11-16, page updated 2026-11-13) still lists 10 ms CPU per invocation on Free and says each isolate has "some built-in flexibility" for a Worker that "infrequently runs over" the limit, while one that consistently hits it is terminated. That matches what the spike saw. We treat the flexibility as a margin for rare tails and cold starts, never as budget.

1. **Library: htmlparser2 12** (`xmlMode`), our own mapper. feedsmith is rejected: 2-3x the CPU on typical feeds, 31-71 ms cold first parse, and a cap can't reduce its cost because it builds the full tree first. No feedsmith or fast-xml-parser dependency.
2. **`MAX_ITEMS_PER_FETCH` = 50**, implemented as a true early stop (the tokenizer stops consuming input after the 50th item closes), not parse-then-slice.
3. **`MAX_BODY_BYTES` = 1 MiB (1,048,576 bytes)**, down from 2 MB, enforced by `safeFetch` while streaming (`too_large`). It may be raised to 2 MiB only if TID-012's deployed benchmark shows body read + hash at 2 MiB keeps the full refresh within the targets below; that change needs an update to this ADR.
4. **Per-item content cap stays at 100 KB**, applied while accumulating text (stop appending at the cap), not by truncating afterwards.
5. **We keep `content:encoded`.** Dropping it (option b) would remove full article text for many feeds, and we have no readability fallback (non-goal). Cutting to 25 items wouldn't help either: the p99 tail is not size-driven (the 25 KB feed had p99 12.7 ms; the no-op baseline 0.68 ms), so it is GC/JIT noise that caps can't remove.
6. **CPU target restated (replaces "typical p99 ≤ 8 ms", which no option met).** For a full refresh invocation that parses a changed feed of up to 1 MiB:
   - **Gate: zero `exceededCpu` outcomes** over ≥ 200 deployed invocations per fixture, and **p95 ≤ 8 ms** for the whole invocation (fetch handling, body read, hash, parse, dedup, D1 calls).
   - Parse alone (spike basis): p95 ≤ 6 ms. Measured 4.4-6.9 ms with early stop.
   - **p99 and cold first refresh are recorded, not gated.** Expect p99 of about 10-13 ms and a cold first parse of 13-23 ms; both rely on the isolate flexibility above.
   - Production: `exceededCpu` < 1% of refresh invocations (TID-024 AC4). Any killed refresh is recorded as `cpu_limit` and backed off (spec §7.4).
7. **If TID-012 misses the gate**, in this order: (a) lower `MAX_ITEMS_PER_FETCH` to 25 and re-measure; (b) cap stored content per item at 50 KB; (c) apply the user's Q6 rule (stay free and show oversized feeds as failing unless more than 5% of feeds are affected, then ask about Workers Paid with numbers).
8. **Huge fixture (TID-002 AC3): rejected as `too_large`** while the body streams in, before any parse. A 3.3 MB feed is never parsed.
9. **Unmeasured costs move to TID-012.** Body read into memory, `DigestStream` SHA-256, dedup-key hashing, and the D1 calls' JS-side CPU are measured there on the deployed Free plan as part of the gate above. TID-011 proves the early stop and the content cap with unit tests and ships a Node benchmark script (informational; Node timings don't predict Workers CPU).
10. **Spike fixtures are not merged.** `e2e/fixtures/generate-feeds.ts` (`rss-small`, `rss-typical`, `atom-typical`, `rdf-typical`, `rss-large`, `rss-huge`) generates the same sizes deterministically, and 4.7 MB of lorem ipsum doesn't belong in git. The exact spike bytes stay reproducible from `spikes/tid-002/gen-fixtures.mjs` on branch `tid-002-parse-spike`. TID-002 AC4 is amended to match.

### Known limitation (accepted for MVP)

Because we stop after the first 50 items in document order, a feed that lists items oldest-first and has more than 50 items will never show new items. Such feeds are rare. Detecting them (ascending dates across the parsed items) is logged as risk R11 in the spec. No MVP work.

### Consequences

- Spec §7.3, §9.7, §9.8, §10.6, NFR-6, FR-FH-1 copy and risk R1 updated to these numbers.
- TID-010 AC4 uses 1 MiB + 1 byte. TID-011 gains early-stop, content-cap and benchmark criteria. TID-012 gains the deployed CPU gate.
